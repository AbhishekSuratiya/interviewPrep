React Native internals

JavaScript at the top. Pixels at the bottom.

Everything interesting in React Native happens in the gap between those two lines — which thread the work runs on, how it crosses into native code, and what has to be serialized to get there. The old architecture and the new one answer that differently.

The whole thing, on three threads

Where the work actually runs

React Native has always had three threads that matter. The architectures differ mainly in how much sits in the middle column and what it costs to get there. Flip the switch.

Legacy pipeline

The old architecture, step by step

This is roughly what shipped from 2015 until the new architecture went default. Every stage is still worth knowing — most of it survives, just relocated.

01

Metro bundles, Babel transpilesBuild time

Metro is the bundler. Babel is the transform that turns JSX into React.createElement calls and modern syntax into something the engine accepts. The output is one JavaScript bundle. Metro doesn't understand JSX itself — it orchestrates Babel.

02

React builds an element treeJS thread

Running the bundle produces a tree of React elements — plain objects describing what the UI should be. There is no DOM here, so calling it a "virtual DOM" is a web habit. In React Native it's just the element tree.

03

The stack reconciler diffs itJS thread

Recursive traversal, comparing the new tree against the previous one to decide what mounts, updates, and unmounts. It uses the same heuristics that keep diffing at O(n) instead of O(n³): different element types replace the subtree, and keys identify siblings across renders. Because it's a recursive call stack, it cannot be interrupted — once a render starts, it runs to completion.

04

Changes are serialized across the bridgeBridge

The JS side batches its native calls, encodes them as JSON, and posts them over an asynchronous queue. Native decodes and applies them. Two runtimes that share no memory, talking by message passing.

05

The shadow tree is built and laid outShadow thread

Native constructs a parallel tree of shadow nodes and hands it to Yoga, the C++ Flexbox engine, which computes every frame's position and size. Yoga has been here since the beginning — it did not arrive with the new architecture.

06

UIManager mounts real viewsUI thread

The computed layout is applied to actual UIView and android.view.View instances. This renderer is the one now called Paper — the name was invented retroactively, once Fabric needed something to be distinguished from.

Why it was replaced

Three things the bridge could not do

Asynchronous only

No synchronous reads

Everything is a queued message, so JavaScript can never ask native a question and get an answer in the same tick. Measuring a view, reading scroll offset, or responding to a gesture on the same frame was impossible.

Serialization cost

Everything becomes JSON

Every prop, every event, every frame of a scroll or animation gets encoded to a string and decoded on the other side. The cost scales with how much you're moving, which is exactly wrong for high-frequency interaction.

Congestion

One queue, no priorities

A large list update and a touch response sit in the same queue in arrival order. Bursts of traffic delay the messages that actually needed to land this frame — the classic dropped-frame-while-scrolling problem.

New architecture

Four pieces, one idea

The idea is shared memory instead of message passing. Everything below follows from being able to hold a native object directly from JavaScript.

Foundation

JSI — JavaScript Interface

A thin C++ layer that lets JavaScript hold references to native objects and call their methods directly, synchronously, with no serialization. It also decouples React Native from any one engine: JSC, Hermes, or in principle V8 all sit behind the same interface.

Everything else here is built on top of this one capability.

Renderer

Fabric

The rendering system rewritten in C++ and shared across platforms. React's committed tree drives the creation of an immutable shadow tree; Yoga computes layout; the mount phase applies it to native views. Because there's no queue, the pipeline can run synchronously when a frame demands it.

Immutability is what makes concurrent rendering safe — an in-progress tree is a new tree, not a mutation of the one on screen.

Native modules

TurboModules

Native modules exposed through JSI as objects JavaScript can call directly. The big win is laziness: modules are instantiated the first time they're actually used, rather than every module being constructed at startup because the bridge needed the full registry up front.

Faster cold start, and calls that can return a value synchronously when appropriate.

Type safety

Codegen

You declare a module or component's interface in typed JavaScript — a TypeScript or Flow spec file. At build time, Codegen generates the matching C++, Objective-C, and Java glue.

This is what makes the other two safe. Without a shared contract, direct memory access between an untyped language and a typed one is a crash waiting to happen. Mismatches become build errors instead of runtime errors.

React side

Fiber, and what it did not change

Fiber is a React change, not a React Native change — but it's the reason the new renderer can be interrupted at all.

01

The tree becomes a linked list

Each fiber node holds child, sibling, and return pointers, plus state, props, effects, and the work still to do. Traversal no longer needs the call stack, because the tree carries its own cursor.

02

Two trees: current and work-in-progress

React builds the next tree alongside the one on screen and swaps them on commit. Rendering can be abandoned halfway with nothing visible ever having been touched.

03

The work loop and scheduler

Work is processed in units. After each unit React checks whether it should yield to something more urgent — typing, a gesture — and resume later. Priority lanes decide what jumps the line.

04

The diffing algorithm is unchanged

Same heuristics, same O(n), same rules about types and keys. Fiber changed the data structure and the scheduling around the diff — not the comparison itself. There is no "new diffing algorithm" to name.

The engine

JSC to Hermes, and why no JIT

A separate story from the renderer, often conflated with it. This one is about how the JavaScript itself gets executed.

Starting point — JavaScriptCore

Borrowed from Safari

React Native shipped on JSC. On iOS it's part of the OS. On Android there is no system engine, so a full copy of JSC was bundled into the APK — a general-purpose desktop-class engine, tuned for long-lived browser sessions rather than an app that opens and closes.

The mismatch

Optimized for the wrong shape of workload

A browser engine assumes it has time to warm up: parse, interpret, watch which functions are hot, then compile those to machine code. A mobile screen is judged on the first few hundred milliseconds. Parsing a large bundle before anything can run was a direct cost on time-to-interactive, and the engine binary itself added weight and memory.

2019 — Hermes on Android

Move the parsing to build time

Hermes compiles the bundle to its own bytecode ahead of time, during the build. The app ships bytecode instead of source, so startup skips parsing entirely and can memory-map the file rather than loading it. Smaller download, lower memory, faster first frame.

2021 onward

iOS support, then the default

Hermes became available on iOS and is now the default engine for new projects. JSI is what made the swap tractable — the renderer talks to an interface, not to a specific engine.

The constraint

Interpretation, not JIT

Hermes executes bytecode with an interpreter. It does not compile to machine code at runtime. On iOS that isn't a choice — App Store rules forbid writing to memory pages and then executing them, which is what a JIT fundamentally does. Hermes stays within the rules on both platforms by not having one.

The tradeoff

What you give up without a JIT

A JIT watches code as it runs. When a function turns out to be hot and to always receive, say, two numbers, it compiles a specialized machine-code version for that exact case and guards it — if a string ever shows up, it bails back to the interpreter. That's how a browser makes a tight loop fast, and it's precisely what Hermes cannot do. Repeated work stays at interpreter speed.

Which is also the answer to "why not just compile JavaScript to machine code up front?" You can't produce good machine code without knowing types, and JavaScript doesn't have them until runtime. Ahead-of-time compilation either emits generic code that type-checks on every operation — no faster than interpreting — or emits a specialized variant for every combination the compiler can imagine, which explodes the binary. The type information only exists while the program is running, so the optimization has to happen there too.

Hermes takes the deal because mobile apps are dominated by startup and by UI work, not by long-running numeric loops. Bytecode is also architecture-neutral: the same artifact runs on ARM and x86, on both platforms. Machine code would not be.

Corrections worth having ready

Things that sound right and aren't

"The new architecture uses a new diffing algorithm."

The diff is the same. Fiber changed the data structure and the scheduler around it, which is what enables pausing and resuming. If you're asked to name the new algorithm, the correct answer is that there isn't one.

"Yoga came with Fabric."

Yoga has computed Flexbox layout since the original architecture. What changed is where the shadow tree lives and that reaching it no longer requires a serialized hop.

"React Native has a virtual DOM."

There's no DOM on mobile. It's a React element tree, and after reconciliation, a fiber tree. The shadow tree is the native-side counterpart.

"Hermes made the app faster to run."

Hermes mainly improves startup time, bundle size, and memory. Without a JIT, steady-state execution of hot code is generally slower than JSC on a warmed-up path. The win is at the beginning, which is where mobile is judged.

"JSI replaced the bridge, so the bridge is gone."

In a fully migrated app, yes — but the bridge remains for interop while legacy modules and components are still in the tree. Migration is incremental, and most real codebases run both for a while.
