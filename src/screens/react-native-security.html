The mechanism · end to end

What SSL pinning actually does

To understand pinning you have to understand the hole it closes. Normal TLS trusts any certificate signed by a CA the device trusts — and the device trusts hundreds of CAs, plus any a user (or attacker) installs.

Keys first: what lives where

The server holds a private key that never leaves the server. Its matching public key is embedded in the server's TLS certificate, which is public by design — anyone connecting receives it. Asymmetric crypto means data (or a signature) produced with the private key can only be verified/undone with the public key, and vice-versa. The client never has the private key; pinning is about the client refusing to trust any public key except the specific one(s) it was told to expect.

The handshake, step by step

01

Client says hello

The app opens a TLS connection to api.myapp.com — sending supported cipher suites, TLS version, and the hostname (SNI). No secrets yet.

02

Server presents its certificate chain

The server returns its leaf certificate (containing its public key), plus the intermediate CA cert(s) that chain up to a trusted root. Crucially, it also signs part of the handshake with its private key — proving it actually holds the key the certificate claims.

03

Standard validation (this is the weak point)

The OS checks the chain: is it signed by a CA in the device's trust store, is the hostname right, is it unexpired? If yes, TLS is happy — and it does not care which CA. A proxy that installed its own CA passes this check.

04

Pin check (the extra gate you add)

Before trusting the connection, the app computes the SHA-256 hash of the presented certificate's Subject Public Key Info (SPKI) and compares it to the pin(s) baked into the app. Match → continue. Mismatch → abort the connection, fail closed, no data sent.

05

Key exchange & encrypted traffic

Client and server run an (EC)DHE exchange to derive symmetric session keys. All application data is then encrypted with those keys. The private key never travels; it's only used to prove identity during the handshake.

How this stops a man-in-the-middle

A MITM proxy sits between the app and the server and installs its own CA certificate on the device (a common “debug” or corporate-managed setup). It then presents the app a certificate for api.myapp.com signed by its CA. Under normal TLS this passes — the device trusts that CA — so the proxy decrypts your traffic, reads it, and re-encrypts to the real server. Nobody notices.

Why the pin defeats it The proxy does not have your server's private key, so it cannot present your server's public key — it must use its own. When the app hashes the presented public key, it won't match the pin, and the connection is dropped before a single byte of application data is sent. The attacker's certificate is “valid” to the OS but wrong to your app. That's the whole game.
The one case pinning does NOT save you from If the server's private key itself leaks, the attacker can present your real public key — which matches the pin — and MITM successfully. Pinning trusts that key; a stolen key is trusted too. The only fix is to rotate to a new key pair and get clients onto a new pin (see rotation below). This is exactly why you never pin just one key.
What you pin, and why

Hash the public key — and keep more than one

Two decisions define a healthy pinning setup: what value you pin, and how many. Getting either wrong is how teams brick their own apps.

Pin the SPKI hash, not the certificate, not the raw key

You pin a SHA-256 hash of the public key (the SPKI), typically base64-encoded, rather than the full certificate or the raw key bytes. Why the hash of the public key specifically:

You could pin…Problem
The whole certificateCertificates expire and get reissued constantly (Let's Encrypt every 90 days). Every renewal changes the cert → every renewal breaks the app. Brittle.
The public key (SPKI) hash ✓Survives certificate renewal as long as you reuse the same key pair when reissuing. Compact, stable, and it's what OkHttp / network_security_config / TrustKit all expect.
The raw public key bytesWorks, but larger to embed and no privacy benefit; the hash is the standard, and it's what the tooling emits.

You can pin at different levels of the chain: the leaf key (strictest, but rotates most often), or an intermediate CA key (survives leaf renewals as long as the CA/intermediate is unchanged, at the cost of trusting anything that intermediate signs). A common setup pins the leaf SPKI plus a backup.

Why you MUST keep multiple pins

Pins are baked into a released app. If you pin exactly one key and that key ever has to change — expiry, compromise, a CA migration — every installed client that only knows the old pin can no longer connect, and you can't fix them without an app-store update that users install on their own slow schedule. You've locked yourself out of your own users.

The backup-pin rule (RFC 7469) Always ship at least two pins: the key currently in use, plus a backup key you are not using yet — generated in advance and kept offline in cold storage. Because clients already trust the backup, you can switch the server to it instantly during an incident with zero client breakage, then generate the next backup. One pin is a single point of failure; the backup is your escape hatch.

What a leaf + backup pin set looks like (Android)

<pin-set expiration="2026-12-31">
  <!-- Current leaf public-key hash -->
  <pin digest="SHA-256">r/m5B44373O61nnd94LA67DMq45L8gQI...=</pin>
  <!-- Backup key — NOT in use yet, kept offline for rotation -->
  <pin digest="SHA-256">YLh1ua5N81AY_MD16AYPq1c5L8gQI...=</pin>
</pin-set>
Two ways to implement it

Native pinning vs a JS library

You can enforce pinning at the OS networking layer (native config) or through a React Native library that ships its own network client. They fail in opposite directions — the trade-off is coverage vs. update flexibility.

Option A · Native (OS-level)

Android: network_security_config.xml (or OkHttp CertificatePinner). iOS: an NSURLSession auth-challenge delegate or TrustKit. The pin is enforced by the platform's own networking stack, below JavaScript.

Pros

  • ✓ Covers all traffic automatically — fetch, Axios, image loading, WebViews, and third-party SDKs — because it's enforced at the OS socket layer.
  • ✓ Hardest to bypass; runs in native code, not the JS bundle.
  • ✓ Uses first-class platform APIs that track OS TLS changes.

Cons

  • ✗ The pin is compiled into the binary / native config — you can't update the public key on the fly. Changing it needs a full app-store release.
  • ✗ Per-platform setup (separate Android and iOS configuration).
  • ✗ A rotation mistake can only be fixed by shipping and getting users to update — slow and partial.

Option B · JS library (e.g. react-native-ssl-pinning)

Libraries like react-native-ssl-pinning expose their own fetch that performs the pin check. Pinning applies only to requests made through that function.

Pros

  • ✓ One cross-platform JS API; quick to wire up.
  • ✓ Pin config lives in JS, so it can be updated via CodePush / OTA without an app-store release (with big caveats — see rotation).
  • ✓ Easy to point at a remote, signed pin list for dynamic rotation.

Cons

  • ✗ You can't cover the whole app. Only calls that go through the library's fetch are pinned. Default fetch, Axios, <Image> loads, analytics/ads SDKs, and WebViews are unprotected unless you route every one through it — which is often impossible for third-party code.
  • ✗ Extra dependency that can lag OS/TLS changes and add native build friction.
  • ✗ Enforced in the JS layer — a determined attacker on a rooted device (Frida) has an easier hook point than native.
The senior takeaway Native = total coverage but rigid updates. Library = flexible updates but partial coverage. Many teams use native pinning for whole-app protection and drive it from a remotely fetched, signed pin list so keys can rotate without a store release — getting coverage and flexibility. If you use a library, you must consciously route every network path through its client, or accept that the rest of your traffic isn't pinned.
Rotation · the part that bricks apps

When and how to rotate pins

Rotation is where pinning gets dangerous. A pin is a promise baked into apps already on phones; changing it wrong means those phones stop talking to your server.

When to rotate

Scheduled

Ahead of certificate/key expiry, and periodically as hygiene. Note: if you reuse the same key on cert renewal, the SPKI pin doesn't change and no client update is needed — only key changes force a pin change.

Emergency

On a suspected or confirmed private-key compromise, a CA breach, or a forced CA migration. This is the scenario the backup pin exists for.

Structural

Changing hosting/CDN or TLS provider that alters the presented key or intermediate. Anything that changes the pinned public key requires a planned rotation.

How to rotate safely (native)

01

Ship the next key's pin before you need it

Generate the backup key pair in advance and include its SPKI hash as a second pin in a released app. Now installed clients trust both the current key and the future one.

02

Wait for adoption

Let the release roll out so the large majority of active users are on a build that knows the backup pin. This is why you plan rotation weeks ahead — you're racing the update-adoption curve.

03

Switch the server to the backup key

Issue a new certificate using the pre-shipped backup key and deploy it. Clients that already trust that pin connect seamlessly; nothing breaks.

04

Mint the next backup

Generate a fresh offline backup key and ship its pin in the next app release, so you're always one key ahead. Rotation is a rolling pipeline, never a one-off.

The failure mode to name in an interview Rotating a native pin without a pre-shipped backup instantly bricks every client that hasn't updated — they refuse the new key, and they can't be fixed remotely because pinning has cut them off. Recovery means an emergency app-store release and hoping users update. This is the single biggest operational risk of pinning, and the reason backup pins are non-negotiable.

Rotating via a library + code push (OTA)

Because a library's pins live in JS, you can update them with CodePush / EAS Update and rotate without an app-store release — which is the main reason teams reach for a library. It genuinely solves the “native pins are frozen in the binary” problem. But there are sharp edges:

Why it can work

  • ✓ The OTA update service (Expo/Microsoft) is usually a different, un-pinned domain, so a client with a broken pin to your API can still download the fix.
  • ✓ Config-only OTA pin updates are allowed by store policies (no native code change).
  • ✓ Turns a multi-day store rotation into minutes.

Why it's risky

  • ✗ Only pins the JS-library traffic — everything else in the app is still unprotected.
  • ✗ You're now trusting the OTA channel as part of your security boundary; it must be signature-verified, or a bad push could weaken/replace your pins.
  • ✗ Code push can't change native pinning or native modules — only the JS bundle.
Best of both A robust setup: native pinning for whole-app coverage, backed by a remotely fetched, cryptographically signed pin list and always-present backup pins. You get OS-level coverage, and you can rotate keys without waiting on the store — the flexibility people chase with a library, without giving up coverage.
Implementation Patterns

Pinning & device-integrity code

Android · network_security_config.xml (covers all app traffic)

<network-security-config>
  <domain-config>
    <domain includeSubdomains="true">api.myapp.com</domain>
    <pin-set expiration="2026-12-31">
      <pin digest="SHA-256">r/m5B44373O61nnd94LA67DMq45L8gQI...=</pin>  <!-- current -->
      <pin digest="SHA-256">YLh1ua5N81AY_MD16AYPq1c5L8gQI...=</pin>  <!-- backup -->
    </pin-set>
  </domain-config>
</network-security-config>

JS library · pinning applies ONLY to this fetch

import { fetch } from 'react-native-ssl-pinning';

// ⚠️ Only requests through THIS fetch are pinned.
// Default fetch/Axios/<Image>/SDKs are NOT covered.
await fetch('https://api.myapp.com/me', {
  method: 'GET',
  sslPinning: { certs: ['cert-current', 'cert-backup'] }, // current + backup
  headers: { Accept: 'application/json' },
});

Extract the SPKI pin from a server (for either approach)

# Hash the server's public key exactly as the pin format expects
openssl s_client -connect api.myapp.com:443 -servername api.myapp.com \
  | openssl x509 -pubkey -noout \
  | openssl pkey -pubin -outform der \
  | openssl dgst -sha256 -binary \
  | openssl enc -base64
# → r/m5B44373O61nnd94LA67DMq45L8gQI...=

Device-integrity gate (defense in depth, not a pinning substitute)

import JailMonkey from 'react-native-jailmonkey';
import { Alert, BackHandler } from 'react-native';

export function enforceDeviceSecurity() {
  if (JailMonkey.isJailBroken() || JailMonkey.hookDetected()) {
    Alert.alert('Security Exception',
      'Untrusted environment detected. App closing for security.',
      [{ text: 'OK', onPress: () => BackHandler.exitApp() }]);
    return false;
  }
  return true;
}
Interview Pitfalls

Client Security Realities

"SSL pinning stops a man-in-the-middle even if the attacker steals the server's private key."

False. A leaked private key lets the attacker present your real public key, which matches the pin. Pinning trusts that key. The only remedy is to rotate to a new key pair and move clients onto a new pin — which is why backup pins exist.

"A pinning library secures the whole app's network traffic."

False. Library pinning only covers requests made through the library's own fetch. Default fetch, Axios, image loads, WebViews, and third-party SDKs are unpinned unless routed through it. Native config pins all traffic.

"We only need to pin one key — the current one."

Dangerous. A single pin is a single point of failure. If that key must change, every un-updated client is bricked. Always ship a backup pin (an offline key not yet in use) so you can rotate without breaking clients.

"Pin the certificate so it's tightly locked down."

Brittle. Certificates are reissued frequently; pinning the whole cert breaks on every renewal. Pin the public-key (SPKI) hash and reuse the key across renewals so the pin stays stable.

"Client-side obfuscation and pinning make an app unhackable."

False. Client code runs on untrusted hardware. Pinning and obfuscation raise the attacker's cost; they don't make secrets safe. True secrets and authorization must live on the backend.
