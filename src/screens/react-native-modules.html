Native Interoperability

Custom Native Modules. The old Bridge vs the new TurboModule.

A native module exposes platform code (Kotlin/Java, Swift/Obj-C) to JavaScript. The old way registered it by hand and called it over the serialized bridge; the new way starts from a typed spec, generates the glue with Codegen, and calls straight through JSI. Here's the step-by-step difference, a working example of each, and exactly which files you touch.

Bridge · @ReactMethod TurboModule · JSI TypeScript Spec Codegen ReactPackage
Step by step

Creating a module: Bridge vs TurboModule

The same goal — expose a native method to JS — done both ways. Read across each row to see what changed.

Step Old Architecture (Bridge) New Architecture (TurboModule)
1Create native class (MyModule.java / MyModule.kt) extending ReactContextBaseJavaModuleCreate a TypeScript spec (NativeMyModule.ts) defining the API
2Implement getName()Run Codegen to generate native interfaces
3Annotate methods with @ReactMethodImplement the generated abstract class/interface (NativeMyModuleSpec)
4Create a ReactPackageUsually no custom ReactPackage (module is registered via the generated provider)
5Override createNativeModules() and return the moduleRegister the TurboModule using the generated delegate/provider
6Add the package in MainApplication.kt (getPackages())Enable the New Architecture & Codegen configuration
7JS accesses it via NativeModules.MyModuleJS imports the generated module (TurboModuleRegistry.getEnforcing())
8Calls go through the Bridge (serialization)Calls go directly through JSI (no Bridge)
The one-sentence why Old modules are registered by hand and typed by convention — a mismatch between JS and native surfaces only as a runtime crash, and every call is serialized to JSON over the async bridge. New modules are generated from a typed spec, so mismatches are build errors, modules load lazily, and calls can run synchronously over JSI with no serialization.
Example · Old Architecture (Bridge)

A multiply module, the old way

Four files: the module, a package, registration in MainApplication, and the JS call.

android/app/src/main/java/com/myapp/MyModule.kt 
class MyModule(ctx: ReactApplicationContext) : ReactContextBaseJavaModule(ctx) {
  // Step 2: the name JS will look up on NativeModules
  override fun getName() = "MyModule"

  // Step 3: @ReactMethod exposes it to JS. Async result via Promise/callback
  @ReactMethod
  fun multiply(a: Double, b: Double, promise: Promise) {
    promise.resolve(a * b)   // answer is serialized back over the bridge
  }
}
android/app/src/main/java/com/myapp/MyPackage.kt 
class MyPackage : ReactPackage {
  // Step 4 + 5: create the module and return it in the list
  override fun createNativeModules(ctx: ReactApplicationContext) =
    listOf(MyModule(ctx))
  override fun createViewManagers(ctx: ReactApplicationContext) =
    emptyList<ViewManager<*, *>>()
}
android/app/src/main/java/com/myapp/MainApplication.kt 
override fun getPackages(): List<ReactPackage> =
  PackageList(this).packages.apply {
    add(MyPackage())   // Step 6: register your package
  }
JS — anywhere in your app 
import { NativeModules } from 'react-native';
// Step 7: access via NativeModules; call is async over the bridge (Step 8)
const result = await NativeModules.MyModule.multiply(3, 7); // 21
iOS equivalent (old) Same shape in Obj-C: a class with RCT_EXPORT_MODULE() and RCT_EXPORT_METHOD(multiply:...) in MyModule.m. No spec, no codegen — just macros the bridge reads at runtime.
Example · New Architecture (TurboModule)

The same module, as a TurboModule

Start from a typed spec, let Codegen produce the native interface, implement it, and enable the New Architecture.

src/specs/NativeMyModule.ts  ·  must be prefixed Native 
// Step 1: the contract. Codegen reads this file.
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';

export interface Spec extends TurboModule {
  multiply(a: number, b: number): number;   // can be SYNCHRONOUS via JSI
}
// Step 7: JS imports this directly — typed, no NativeModules lookup
export default TurboModuleRegistry.getEnforcing<Spec>('MyModule');
package.json  ·  Codegen config (Step 2 + 6) 
"codegenConfig": {
  "name": "MyModuleSpec",
  "type": "modules",
  "jsSrcsDir": "src/specs"
}
# Step 6: turn the New Architecture ON
# android/gradle.properties → newArchEnabled=true
# iOS → RCT_NEW_ARCH_ENABLED=1 bundle exec pod install
android/app/src/main/java/com/myapp/MyModule.kt 
// Step 3: extend the class Codegen generated from the spec
class MyModule(ctx: ReactApplicationContext) : NativeMyModuleSpec(ctx) {
  override fun getName() = "MyModule"

  // No @ReactMethod — the generated base already declares it (typed)
  override fun multiply(a: Double, b: Double): Double {
    return a * b   // Step 8: returned straight to JS over JSI, no serialization
  }
}
MainApplication.kt  ·  register via the TurboModule provider (Step 4 + 5) 
// A BaseReactPackage exposes the module by name + declares it to the registry
class MyPackage : BaseReactPackage() {
  override fun getModule(name: String, ctx: ReactApplicationContext) =
    if (name == "MyModule") MyModule(ctx) else null
  override fun getReactModuleInfoProvider() = ReactModuleInfoProvider {
    mapOf("MyModule" to ReactModuleInfo(
      "MyModule", "MyModule", false, false, false, isTurboModule = true))
  }
}
JS — same call site, now typed & synchronous-capable 
import MyModule from './specs/NativeMyModule';
const result = MyModule.multiply(3, 7); // 21 — can be synchronous, fully typed
What changed in practice You wrote a spec instead of relying on @ReactMethod, ran Codegen (it runs during the native build) to get NativeMyModuleSpec, implemented that generated class, and flipped newArchEnabled. In return: JS/native mismatches are compile errors, the module loads on first use, and the call skips the bridge.

Interview Pitfalls

Native Module Myths

"TurboModules removed getName() and the ReactPackage entirely."

Not quite. You still implement getName() and still register the module through a package in getPackages() — but the package is a BaseReactPackage that declares the module to the TurboModule registry, and the method signatures come from the generated spec, not @ReactMethod.

"Codegen is a separate command you run manually."

Usually no. Codegen runs automatically as part of the native build (Gradle / pod install) from your codegenConfig. It reads the Native*.ts spec and emits the C++/Java/Obj-C interfaces you implement.

"All TurboModule calls are synchronous."

Only when appropriate. JSI allows synchronous returns (great for cheap getters), but long-running work should still return a Promise so it doesn't block the JS thread. The win is that sync is now possible, not mandatory.
