React Native Performance Engineering

The 60 FPS Stack. Eliminating jank across lists, images & animations.

Most React Native jank is one of three things: a list that rebuilds views instead of recycling them, a render function that re-runs the whole tree on every keystroke, or an animation stuck behind a busy JS thread. This guide covers all three — and, just as importantly, how to measure which one you actually have before you touch a line of code.

Lists · Part 1

Start with the default: FlatList

Before reaching for a library, know what the built-in list already does. Most people underestimate FlatList — and then misuse it in the ways that make it slow.

FlatList is React Native's virtualized list. Unlike ScrollView, which mounts every child up front, FlatList only renders the items in (and just around) the viewport. As you scroll, items that leave the window are unmounted and new ones are mounted. That windowing is why it can handle thousands of rows at all.

The distinction that matters ScrollView renders all children immediately — fine for a handful of items, fatal for a feed. FlatList virtualizes: it keeps a small window of mounted rows and blank-space placeholders for the rest. If your data set is bounded and tiny, ScrollView is actually fine and simpler. Everything below assumes a long, scrolling list.

The props that control how much work FlatList does

These are the levers. Most jank is a FlatList using defaults that don't match the shape of its data.

Where FlatList actually breaks Even tuned perfectly, FlatList creates and destroys component + native view instances as items cross the viewport edge. On a fast fling, it can't mount rows fast enough — you get blank white cells that fill in a beat later. That mount/unmount churn is the ceiling you hit on image-heavy feeds, and it's the exact thing FlashList removes.
Lists · Part 2

FlatList vs FlashList

FlashList (by Shopify) is a near drop-in replacement built on native cell recycling. Same mental model, very different engine underneath.

ConcernFlatListFlashList
Off-screen rowsUnmounts & destroys the viewRecycles the view, swaps its data
Fast-scroll blank cellsCommon (mount can't keep up)Largely eliminated
SizingMeasures each row, or needs getItemLayoutUses estimatedItemSize to pre-allocate
Memory on long listsGrows with window sizeRoughly constant (bounded pool)
Mixed row typesNo first-class supportgetItemType keeps separate recycle pools
APIBaselineNearly identical — usually a rename + one prop
How recycling actually works Instead of one native view per data row, FlashList keeps a small pool of views — roughly “one screen plus a margin.” When a row scrolls off the top, its view isn't destroyed; it's moved to the bottom and re-bound to new data. This is the same idea as Android's RecyclerView and iOS's UICollectionView. Because there's no create/destroy on scroll, the CPU spikes that cause blank cells disappear.
Lists · Part 3

The FlashList props that matter

Recycling only pays off if you feed it the right hints. These are the props interviewers expect you to name.

PropWhy it matters

getItemTypeReturn a type string per row (e.g. 'header' | 'post' | 'ad'). FlashList keeps a separate recycle pool per type, so a text row never gets re-bound into a video cell. Essential for mixed feeds.

The best way to use FlashList

Recycling changes one rule you can get away with breaking in FlatList: a recycled row must never keep its own local state, because that state will leak into whatever data it's re-bound to next.

01

Set a realistic estimatedItemSize

Run once in dev — FlashList logs the exact average it observed. Use that. A wildly wrong estimate reintroduces blank space and layout thrash.

02

Give every distinct row shape a getItemType

Headers, ads, text posts, and media posts should each be their own type. This keeps recycle pools clean and stops layout jumps when different shapes share a cell.

03

Keep rows stateless and derive everything from props

No useState that must persist per item. Drive selected/expanded/liked state from the parent store keyed by item id, so a recycled view always reflects the data it currently shows.

04

Memoize the row and its callbacks

Wrap the row in React.memo and pass renderItem / callbacks via useCallback — exactly as with FlatList (next section). Recycling reduces native churn; memoization reduces JS re-renders. You want both.

Best-practice FlashList

const renderItem = useCallback(({ item }) => (
  <PostCard post={item} onLike={handleLike} />
), [handleLike]);

const keyExtractor = useCallback((item) => item.id, []);

<FlashList
  data={posts}
  renderItem={renderItem}
  keyExtractor={keyExtractor}
  estimatedItemSize={120}            // required — use the dev-logged average
  getItemType={(item) => item.type}   // separate recycle pool per shape
  drawDistance={250}
/>
Re-renders · The other half of list performance

Why your list re-renders every row

Swapping to FlashList fixes native churn. But if the JS side re-renders all rows on every parent update, you've only solved half the problem. This is the single most common list mistake in interviews and in production.

Every time the parent screen re-renders (a state change, a new fetch, a keystroke in a search box), any inline function you pass to the list is created fresh — a brand-new function identity. React compares old props to new by reference, sees a “different” renderItem / onPress, and re-renders the rows. Do that per item across a long list and you get frame drops on interactions that shouldn't cost anything.

✗ What happens without memoization

  • Inline renderItem / onPress get a new reference on every parent render.
  • Props look “changed” by reference → every visible row re-renders.
  • A search box that filters the list re-runs all rows on each keystroke.
  • JS thread saturates → dropped frames, laggy scroll, slow taps.

✓ What memoization buys you

  • Stable function identities via useCallback → props compare equal.
  • React.memo row skips re-render when its item hasn't changed.
  • Only the rows whose data actually changed re-render.
  • Scroll and interactions stay on-budget.

Passing memoized functions to the list

Three things must be stable: the renderItem function, the keyExtractor, and any callback the row calls (like onLike). Wrap each in useCallback so their identity survives across renders.

The problem — new identities every render

// ✗ Each render creates fresh functions → all rows re-render
function Feed({ posts }) {
  return (
    <FlatList
      data={posts}
      renderItem={({ item }) => <PostCard post={item} onLike={() => like(item.id)} />}
      keyExtractor={(item) => item.id}
    />
  );
}

The fix — stable identities + a memoized row

const PostCard = React.memo(function PostCard({ post, onLike }) {
  // re-renders only when `post` or `onLike` actually change
  return (
    <Pressable onPress={() => onLike(post.id)}>
      <FastImage source={{ uri: post.image }} />
      <Text>{post.title}</Text>
    </Pressable>
  );
});

function Feed({ posts }) {
  const handleLike = useCallback((id) => like(id), []);          // stable
  const renderItem = useCallback(({ item }) => (                 // stable
    <PostCard post={item} onLike={handleLike} />
  ), [handleLike]);
  const keyExtractor = useCallback((item) => item.id, []);       // stable

  return (
    <FlatList
      data={posts}
      renderItem={renderItem}
      keyExtractor={keyExtractor}
    />
  );
}

Why memoize the row component itself

Stable callbacks aren't enough on their own. Even with an unchanged onLike, a parent re-render still walks the tree and re-invokes each row function unless the row is told it can bail out. React.memo is that instruction: it wraps the component in a shallow props comparison, so a row skips rendering when its item and callbacks are reference-equal to last time.

The two pieces only work together React.memo on the row makes it able to skip. useCallback on the props makes it actually skip — because memo's shallow compare only passes if the function props are the same reference. Memoize the component but pass an inline arrow, and memo compares equal-value-but-new-reference every time and re-renders anyway. This “I added React.memo and nothing changed” trap is a classic follow-up question.

Pure components & custom comparison

React.memo is the function-component equivalent of a class PureComponent: both do a shallow comparison of props (and, for the class, state) and skip re-rendering when nothing shallow-changed. “Pure” here means the component's output depends only on its props — same props in, same UI out, no side effects — which is exactly what makes skipping safe.

Shallow comparison only checks one level deep. If a row receives a new object/array literal each render (style={{...}}, data={[...]}), the reference differs and memo re-renders. Fix it by hoisting the object, using StyleSheet.create, or memoizing the value — or pass a custom comparator as memo's second argument for precise control:

Custom comparator — re-render only on the fields that matter

const PostCard = React.memo(
  function PostCard({ post, onLike }) { /* ... */ },
  (prev, next) =>
    prev.post.id === next.post.id &&
    prev.post.likes === next.post.likes &&
    prev.onLike === next.onLike        // return true = skip re-render
);
Don't over-memoize Memoization isn't free — useCallback/useMemo store dependencies and run comparisons. On a trivial component that re-renders cheaply, the bookkeeping can cost more than it saves. Reach for it on list rows and expensive subtrees, not every leaf. Measure first (next section), then memoize the hot path.
Measure first

You can't fix what you can't see

The senior move isn't reaching for FlashList — it's proving which thread is the bottleneck before changing anything. Guessing wrong wastes a sprint.

The two frame rates: JS FPS vs UI FPS

React Native runs two threads that each have a frame budget. Reading them separately tells you where the jank lives.

JS thread

Where your logic runs

Renders, state updates, data processing, renderItem. If JS FPS drops but UI FPS holds, the problem is re-renders or heavy JS — reach for memoization, lighter renders, or moving work off the render path.

UI (native) thread

Where views are drawn

Layout, drawing, native view creation. If UI FPS drops, the problem is a heavy view tree or mount/destroy churn — reach for FlashList, flatter view hierarchies, and fewer overdraw layers.

Toggle the built-in overlay with the Dev Menu → Show Perf Monitor (shake the device, or Cmd/Ctrl+M / d in the terminal). It shows both frame rates live while you scroll:

UI60.0 fps
JS38.4 fps
Views412
RAM318 MB

Reading above: UI is fine, JS is dropping to ~38 fps during scroll → the bottleneck is JS-side re-renders, not the native view tree. That points at memoization, not FlashList.

Reading a flame graph

A flame graph turns a recording of the JS thread into a picture of where time went. Each bar is a function call; width = time spent; bars stacked on top of a bar are the functions it called. You read it left-to-right as time, top-to-bottom as call depth. Wide bars are your enemy — they're where the frame budget was burned.

You'd then re-record and confirm the red bar shrank — measure, change, measure again.

Architecture & Internals

How These Libraries Achieve 60 FPS

View Recycling

FlashList by Shopify

FlatList creates and destroys native view hierarchy instances during scrolling, consuming massive CPU cycles. FlashList recycles existing native views (leveraging Android RecyclerView and iOS UICollectionView patterns).

Result: ~10x fewer view creations, near-zero blank spaces during rapid scrolling.

Native Image Caching

FastImage

React Native's stock <Image> lacks robust disk caching and re-downloads remote URLs across app launches. FastImage wraps native battle-tested engines: SDWebImage (iOS) and Glide (Android).

Features: Memory + disk cache, request priority queues, image preloading, and progressive display.

UI Thread Worklets

Reanimated v3

Standard animations pass frame updates over the async bridge. Reanimated uses Worklets — small JS functions compiled to execute directly on the UI Thread via JSI.

Result: Animations and gestures stay at 60–120 FPS even when the JS Thread is 100% blocked by heavy work.

Zero-Provider State

Zustand + MMKV

Large Context Providers trigger re-renders down the entire component subtree. Zustand uses atomic state selectors — re-rendering ONLY components subscribed to the exact changed slice.

Persistence: Paired with MMKV for instant, synchronous disk persistence without Redux boilerplate.

Beyond lists · Whole-app performance

The performance checklist

Lists and re-renders are the runtime story. The other half is what ships in the binary and how fast it starts. These are the levers interviewers expect a senior to rattle off.

Engine & build

Hermes

Ship bytecode, not source

Hermes (default on new RN) compiles your JS to bytecode at build time, so the app skips parsing on startup and memory-maps the bundle instead. Result: faster time-to-interactive, smaller memory, smaller download. It's an interpreter with no JIT — great for startup and UI work, which is what mobile is judged on.

ProGuard / R8 (Android)

Shrink & obfuscate the APK

R8 (the successor to ProGuard) does tree-shaking, minification, and obfuscation of native/Java code in release builds — smaller APK, fewer classes to load. Enable minifyEnabled / enableProguardInReleaseBuilds and keep the rules file tuned so it doesn't strip classes your native modules reflect on.

New Architecture

Fabric + TurboModules

JSI replaces the async bridge with direct, synchronous native calls; TurboModules load lazily instead of all at startup; Fabric renders concurrently. Migrating removes serialization overhead on the hot path and improves cold start.

Startup & bundle

Inline requires + RAM bundles

Lazy-load modules

By default the whole JS bundle is evaluated at launch. Inline requires defer a module's evaluation until it's first used, and the RAM bundle format loads modules on demand. Together they cut the work done before the first screen paints — the biggest lever on cold-start time.

Lazy screens & code-splitting

Don't mount what isn't seen

Lazy-load heavy screens (e.g. navigator lazy options / dynamic import() where supported), defer non-critical work with InteractionManager.runAfterInteractions, and avoid doing expensive setup in the first render pass.

Bundle size hygiene

Measure what you ship

Audit with a bundle visualizer; drop heavy dependencies and moment-style libraries; import sub-paths instead of whole packages; enable Hermes to shrink further. Smaller bundle = faster parse/load and less memory.

Render & assets

Images

Right-size and cache

Serve images at display resolution (don't download a 4K image for a 48px avatar), use FastImage for disk/memory caching and priorities, and prefer WebP. Oversized images are a top cause of memory pressure and scroll jank.

Flatten the view tree

Fewer nodes, less overdraw

Deep nesting and stacked semi-transparent layers cost the UI thread. Collapse unnecessary wrapper Views, avoid overdraw, and keep list rows shallow — the UI thread pays per node, every frame.

Keep work off the render path

Memoize & defer

useMemo for expensive derived values, useCallback for stable handlers, debounce rapid inputs, and move non-urgent work out of render. The cheapest render is the one that doesn't happen.

Memory & leaks

Clean up what you start

Return cleanup functions from effects: clear setTimeout/setInterval, remove listeners (AppState, Keyboard, event emitters), cancel in-flight requests, and stop animations. Leaked subscriptions keep components alive, grow memory, and fire on unmounted screens — a top cause of slow-then-crash on low-RAM devices.

Defer past the transition

InteractionManager

Run heavy work — analytics batching, big fetches, expensive setup — after the navigation animation finishes with InteractionManager.runAfterInteractions, so the screen transition stays at 60 fps instead of competing with your data work on the JS thread.

Defer non-critical work so the transition stays smooth

import { InteractionManager } from 'react-native';
import { useEffect } from 'react';

function DashboardScreen() {
  useEffect(() => {
    // Wait until the screen-transition animation has finished…
    const task = InteractionManager.runAfterInteractions(() => {
      fetchAnalyticsData(); // …then run the expensive work
    });
    // Cleanup: cancel the task AND any subscriptions to avoid leaks
    return () => task.cancel();
  }, []);

  return <View>{/* UI */}</View>;
}
The order to actually do this in 1) Measure and find the hot thread. 2) Fix the list: FlashList for native churn, React.memo/useCallback for re-renders. 3) Fix images and the view tree. 4) Turn on Hermes + R8 and lazy-load the startup path. 5) Re-measure on a release build. Reordering this list — optimizing before measuring — is how you spend a week on the wrong thing.

Interview Pitfalls

Performance Myths & Misconceptions

"FlatList recycles views just like native RecyclerView on Android."

False. FlatList unmounts and mounts React components and native view instances as items enter and exit the viewport. It does NOT recycle existing view nodes. FlashList is what actually implements native cell recycling.

"Adding React.memo to a list row fixes the re-renders."

Only half true. React.memo lets a row skip rendering, but its shallow compare fails the moment you pass an inline arrow or a fresh object as a prop — a new reference every render. You must also wrap callbacks in useCallback (and styles in StyleSheet.create) or memo re-renders anyway.

"useNativeDriver: true makes all Animated API properties run on the UI thread."

False. useNativeDriver: true only supports non-layout properties like opacity and transform. It cannot animate width, height, flex, or backgroundColor. Reanimated 3 handles layout animations on the UI thread via Worklets.

"You should profile on a debug build in the simulator."

False. Debug builds run un-minified JS with dev checks and are far slower — they invent hotspots that don't exist in production. Profile a release/profiling build on a real mid-range device. (React DevTools Profiler is the one exception; it needs a dev build.)

"FastImage is just a wrapper around Image with a caching header."

False. FastImage replaces the native image pipeline with SDWebImage (iOS) and Glide (Android) — native libraries handling disk persistence, memory LRU cache, and priority queues.

Senior Technical Scenario

System Optimization Walkthrough

💬 Question: "A user reports severe scrolling lag (15–20 FPS) on a feed of 3,000 posts with images, avatars, and like animations. Walk through your step-by-step diagnostic and optimization plan."
Optimization Plan:
  1. Measure before touching anything. Open the Perf Monitor and read JS FPS vs UI FPS while scrolling. Record a flame graph (Hermes sampling profiler) to see which functions eat the frame. This decides whether the fix is JS-side (re-renders) or native-side (view churn).
  2. If UI FPS is low — replace FlatList with FlashList. Set a realistic estimatedItemSize and add getItemType for the different card shapes, so views recycle instead of being created and destroyed on every fling.
  3. If JS FPS is low — fix re-renders. Wrap the row in React.memo, and pass renderItem, keyExtractor, and onLike via useCallback so a parent render doesn't re-render every row. Hoist expensive per-row work (date formatting) or memoize it.
  4. Swap Image for FastImage. Enable memory + disk caching with priority loading (priority: high for visible cards) and right-size the assets so a 48px avatar isn't a 4K download.
  5. Move the like animation to Reanimated v3. Convert the heart-pop to useSharedValue + useAnimatedStyle so it runs on the UI thread and never competes with list scrolling on the JS thread.
  6. Re-measure on a release build. Confirm the flame graph's hot bars shrank and both frame rates hold at 60. If not, the bottleneck was somewhere else — repeat from step 1.
