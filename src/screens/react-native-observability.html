Production Monitoring & Telemetry

Observability without slowing the app down.

Monitoring isn't free — every event is a network request, some CPU, and battery. The senior skill is capturing enough signal to debug and understand production without flooding the user's connection: sample, batch, keep rich context in memory and only send it on failure. This covers the tools, the efficiency techniques, and how to track what users actually see.

The landscape

What you monitor, and with what

Three distinct signals, often three different tools: stability, performance, and product behavior.

Stability

Crashes & errors

Unhandled JS exceptions, native (Java/ObjC/C++) signal crashes, ANRs, and handled errors — with stack traces and device context.

Performance

Vitals & traces

Cold/warm start, slow/frozen frames, screen-load and network timings, and traces of slow transactions.

Product

Analytics & funnels

Screen views, feature usage, conversion funnels, and impressions — what users do, not just what breaks.

The cost problem

Monitoring efficiently — don't drown the network

Naive telemetry fires a request per event. On a scrolling feed that's hundreds of requests, draining battery and data and adding latency. Here's how to keep the signal and drop the load.

TechniqueWhat it does
SamplingSend a fraction of performance traces and replays (tracesSampleRate: 0.1). Keep 100% of crashes, sample the noisy stuff. Use replaysOnErrorSampleRate: 1.0 but a low session rate.
Batching / bufferingQueue events in memory and flush in one request on a size or time threshold — not one request per event. The single biggest lever.
BreadcrumbsKeep a rolling in-memory trail (taps, navigations, requests). It costs nothing until an error occurs, then ships with that one report — rich context, near-zero traffic.
Debounce / throttleNever emit per-frame. Coalesce high-frequency signals (scroll, keystroke, impressions) before recording.
Offline queue + backoffPersist events, send when reachable, retry with backoff, prefer un-metered connections and app-foreground/idle.
Trim the payloadgzip; drop verbose fields; strip PII in beforeSend. Smaller, safer, cheaper.
Client-side aggregationCount/summarize on device (e.g. “42 impressions of card X”) and send the rollup, not 42 events.
The best-way answer Capture generously in memory, transmit sparingly. Keep 100% of crashes; sample traces/replays; batch everything else into periodic bulk flushes; keep context as breadcrumbs that only ship on error; aggregate high-frequency events on-device; queue offline and send on a good connection. You get debuggable production data at a tiny fraction of the requests.
Impression tracking

Capturing “the user actually saw this”

To log that a feed item was seen (not just rendered), FlatList/FlashList expose onViewableItemsChanged — it fires as items cross a visibility threshold. It's the right hook for impressions, ads, and “viewed” analytics.

How viewability works

viewabilityConfig defines what “visible” means; onViewableItemsChanged fires with the items that entered/left that state. The key knobs:

ConfigMeaning
itemVisiblePercentThresholdHow much of the row must be on-screen to count (e.g. 60 = 60%).
minimumViewTimeMilliseconds it must stay visible before firing — the anti-fast-scroll filter. Set ~500–1000ms so flinging past doesn't count as an impression.
waitForInteractionDon't count anything until the user first scrolls/taps.
viewAreaCoveragePercentThresholdAlternative: % of the viewport the item covers (for big rows).
The gotcha everyone hits FlatList throws “Changing onViewableItemsChanged on the fly is not supported.” Both the callback and the config must be stable references — define them with useRef (or viewabilityConfigCallbackPairs), never inline. A fresh function each render crashes the list.

The best way to integrate it

01

Stable refs

Put onViewableItemsChanged and viewabilityConfig in useRef so their identity never changes across renders.

02

Filter with minimumViewTime

Require the item to dwell (~500ms+) so a fast scroll doesn't fabricate impressions — this alone kills most of the noise.

03

Dedupe per session

Track already-seen ids in a Set so re-scrolling past an item doesn't double-count.

04

Batch, don't fire per item

Push impressions into a buffer and flush in bulk on an interval / size threshold (and on screen-blur) — one request for many impressions, matching the efficiency rules above.

Batched, deduped impression tracking

function Feed({ posts }) {
  const seen = useRef(new Set());
  const buffer = useRef([]);

  // stable config — visible ≥60% for ≥500ms filters out fast scrolls
  const viewabilityConfig = useRef({
    itemVisiblePercentThreshold: 60,
    minimumViewTime: 500,
  }).current;

  // stable callback — collect, dedupe; DON'T send per item
  const onViewableItemsChanged = useRef(({ viewableItems }) => {
    for (const { item } of viewableItems) {
      if (!seen.current.has(item.id)) {
        seen.current.add(item.id);
        buffer.current.push({ id: item.id, at: Date.now() });
      }
    }
  }).current;

  // flush the buffer in ONE request, periodically
  useEffect(() => {
    const t = setInterval(() => {
      if (buffer.current.length) {
        analytics.track('impressions', { items: buffer.current });
        buffer.current = [];
      }
    }, 5000);
    return () => clearInterval(t);
  }, []);

  return (
    <FlatList
      data={posts}
      renderItem={renderItem}
      viewabilityConfig={viewabilityConfig}
      onViewableItemsChanged={onViewableItemsChanged}
    />
  );
}
Passing it to native analytics Impression capture happens in JS (viewability is a JS-computed event), then the batched rollup is what you hand to the native SDK (Firebase/Amplitude/Sentry) — a single track with many items rather than a native call per row. That keeps the bridge/JSI and the network quiet while still recording every genuine view.
Setup

Sentry — sampled, native, PII-stripped

import * as Sentry from '@sentry/react-native';

Sentry.init({
  dsn: 'https://key@sentry.io/project-id',
  enableNative: true,                 // JS + native crashes in one place
  release: 'com.myapp@1.4.0+42',
  tracesSampleRate: 0.1,              // sample perf — keep 100% of crashes
  replaysOnErrorSampleRate: 1.0,      // replay only when it matters
  replaysSessionSampleRate: 0.0,
  beforeSend(event) {
    // strip sensitive data before it leaves the device
    if (event.breadcrumbs) {
      event.breadcrumbs = event.breadcrumbs.filter(b => !b.data?.url?.includes('/auth/'));
    }
    return event;
  },
});

export default Sentry.wrap(App);

Upload iOS dSYMs and Android R8/ProGuard mapping files in CI so raw addresses symbolicate into real file + line numbers — otherwise native crashes are unreadable.

Interview Pitfalls

Observability Myths

"Track every event in real time for the best data."

Costly and unnecessary. Per-event requests drain battery/data and add latency. Batch, sample, and aggregate on-device — you keep the signal at a fraction of the load.

"onViewableItemsChanged can be an inline function."

No. FlatList throws if the callback or config changes between renders. Wrap both in useRef (or use viewabilityConfigCallbackPairs).

"An item rendering means the user saw it."

False. Virtualized lists render items just off-screen, and fast scrolls flash items by. Use a visibility threshold and minimumViewTime to count a real impression.

"Sampling means you'll miss crashes."

Not if configured right. Sample performance traces and replays; keep error/crash capture at 100%. They're separate rates.
