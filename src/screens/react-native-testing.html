Senior Level Testing

Unit, Integration & E2E. The right test at the right level.

A senior answer isn't “we use Jest.” It's knowing what each test level proves, which tool fits it, and why you want many cheap unit tests and only a few expensive end-to-end ones. This walks the pyramid, the tools for each rung, and the questions you'll actually be asked.

The testing pyramid

Three levels, three purposes

Cost and confidence rise as you climb; speed and count fall. Write lots of the bottom, few of the top.

Level 1 · Unit testing

One piece, in isolation

A unit test verifies a single unit of logic — a pure function, a custom hook, a reducer — with everything it depends on mocked, so a failure points at exactly one place.

Tools: Jest is the runner + assertion library + mocker. For hooks, renderHook from React Native Testing Library. Keep them deterministic — no real timers, network, or native modules.

// util.test.ts — a pure function, no rendering
import { formatPrice } from './util';
test('formats cents to currency', () => {
  expect(formatPrice(1999)).toBe('$19.99');
});

// a custom hook
import { renderHook, act } from '@testing-library/react-native';
test('useCounter increments', () => {
  const { result } = renderHook(() => useCounter());
  act(() => result.current.increment());
  expect(result.current.count).toBe(1);
});
Likely interview questions
  • What makes a good unit test? Fast, isolated, deterministic, tests behavior not implementation, one reason to fail.
  • How do you test a custom hook? renderHook + act() around state updates.
  • Mock vs stub vs spy? Spy observes calls; stub returns canned values; mock asserts on interactions.
  • Why avoid testing implementation details? Tests break on refactors that don't change behavior.
Level 2 · Integration testing

Units working together

Integration tests render a component (or a screen) with its real children, state, context, and navigation, mocking only the boundaries — network and native modules. This is where most RN value lives: it proves the wiring works.

Tools: React Native Testing Library (query by accessibility role/label/text, fire user events), Jest, MSW (Mock Service Worker) to intercept network at the fetch layer, and jest mocks for native modules (MMKV, NetInfo, Reanimated) in jest.setup.js.

import { render, screen, fireEvent, waitFor } from '@testing-library/react-native';

test('submitting the form shows a success message', async () => {
  render(<LoginScreen />);                       // real component + state
  fireEvent.changeText(screen.getByLabelText('Email'), 'a@b.com');
  fireEvent.press(screen.getByRole('button', { name: 'Sign in' }));
  // network mocked by MSW; wait for the resulting UI
  expect(await screen.findByText('Welcome back')).toBeVisible();
});
Likely interview questions
  • Unit vs integration — where's the line? Unit mocks collaborators; integration exercises real collaborators, mocking only I/O boundaries.
  • Why query by role/label instead of testID? It tests what users perceive and doubles as an accessibility check.
  • How do you handle async UI? findBy* / waitFor — never arbitrary sleep.
  • How do you mock the network? MSW at the request layer keeps components unaware they're mocked.
Level 3 · End-to-end testing

The whole app, driven like a user

E2E runs the actual build on a simulator/device and drives it through real flows — launch, navigate, tap, type, assert. Slow and flakier, so reserve it for a few critical journeys (login, checkout).

Which tool for E2E?

ToolStyleStrengthTrade-off
DetoxGray-box (RN-aware)Hooks into the RN/native idle state to auto-wait for the JS thread, animations, timers, and network — far less flaky, no sleep.RN-specific; more setup; you instrument the app.
MaestroBlack-boxDead-simple YAML flows, quick to write, built-in flakiness tolerance. Great DX.Less fine-grained control than Detox for complex assertions.
AppiumBlack-box (WebDriver)Cross-platform (native, hybrid, web) with a huge ecosystem; language-agnostic.Flakier and slower for RN; no RN idle awareness → manual waits.

Detox — a checkout flow (auto-waits, no sleeps)

describe('Checkout', () => {
  beforeAll(async () => device.launchApp({ newInstance: true }));
  beforeEach(async () => device.reloadReactNative());

  it('completes a purchase', async () => {
    await element(by.id('cart-button')).tap();
    await element(by.id('checkout-button')).tap();
    await element(by.id('input-card')).typeText('4242424242424242');
    await element(by.text('Confirm Payment')).tap();
    // Detox waits for the JS thread + animations to settle before asserting
    await expect(element(by.text('Order Successful'))).toBeVisible();
  });
});
Likely interview questions
  • Gray-box vs black-box? Gray-box (Detox) sees app internals to synchronize; black-box (Appium/Maestro) only sees the UI.
  • Why is Detox less flaky? It waits on RN idle instead of fixed timeouts.
  • What belongs in E2E vs integration? Only critical end-to-end journeys; push everything else down the pyramid for speed.
  • How do you keep E2E stable in CI? Stable testIDs, deterministic seed data, retry on known flake, run on a device farm.
Cross-cutting

Mocking & strategy

Native mocks

Keep tests off native

Mock TurboModules and native libs (MMKV, NetInfo, Reanimated, Gesture Handler) in jest.setup.js so unit/integration tests run in Node, fast and deterministic.

Network

MSW over hand mocks

Intercept at the request layer so components stay unaware; reuse the same handlers across many tests and even Storybook.

Coverage ≠ quality

Test behavior, not lines

Chase critical-path confidence, not a coverage number. One good checkout E2E beats 100% coverage of getters.

The senior framing Push tests down the pyramid: if a bug can be caught by a unit or integration test, don't spend a slow, flaky E2E on it. Reserve E2E for a few money-path journeys, make everything else fast, and query by what the user sees so tests survive refactors.
Interview Pitfalls

Testing Myths

"React Native Testing Library is for unit tests."

Mostly integration. RNTL renders a component with its real children/state and fires user events — that's integration. Pure-logic units are just Jest, no rendering.

"100% coverage means well-tested."

False. Coverage measures lines executed, not behaviors verified. You can have 100% coverage and zero meaningful assertions. Test critical paths and edge cases.

"E2E should cover everything for maximum confidence."

Anti-pattern. E2E is slow and flaky; an all-E2E suite is unmaintainable. Keep it thin and lean on fast unit/integration tests below.
