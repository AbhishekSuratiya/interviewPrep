Two problems live here: automating native builds/signing/uploads so a release is one command, and shipping JavaScript fixes over-the-air without waiting on store review. The second one is only safe if you understand exactly what a “bundle” is and where the app loads it from.

Release Architecture

The three jobs of a release pipeline

Code Signing

Certificates & profiles

Sync iOS certs/provisioning profiles and Android keystores across the team and CI. Fastlane Match stores them in an encrypted git repo so every machine signs identically.

Native Build & Submit

Compile & upload

Produce a release .ipa / .aab on a clean runner and push to TestFlight / Play Console. EAS Build, Fastlane gym/gradle, or a Bitrise workflow do this without a developer's laptop.

Live JS Updates

OTA bundle push

Ship JavaScript & asset fixes straight to installed apps (CodePush / EAS Update) — no new binary, no store review — for the class of changes that are JS-only.

Integrating them — the short version

Fastlane

Scripted lanes

  1. gem install fastlane, then fastlane init in ios/ and android/.
  2. Set up signing: fastlane match (iOS) / keystore for Android.
  3. Write a lane: build (gym/gradle) → upload (pilot/supply).
  4. Store secrets in env vars; call the lane from any CI.
Bitrise

Managed workflow

  1. Connect the repo; Bitrise auto-detects the RN project.
  2. Add Steps (install deps, cache, build iOS/Android, deploy) in the editor.
  3. Upload signing files to the Code Signing tab.
  4. Set triggers (push/tag/PR) → runs on managed runners.
EAS

Cloud build + submit

  1. npm i -g eas-cli, eas login, eas build:configure.
  2. Define profiles/channels in eas.json.
  3. eas build --profile production → cloud .ipa/.aab.
  4. eas submit to push to the stores.

Fastlane lane + eas.json

# Fastfile — one command to ship a beta
lane :beta do
  increment_build_number
  match(type: 'appstore')                          # sync certs from encrypted git
  gym(scheme: 'MyApp', configuration: 'Release')   # build .ipa
  pilot(skip_waiting_for_build_processing: true)   # upload to TestFlight
end

// eas.json — cloud build tied to an OTA channel
{ "build": { "production": { "autoIncrement": true, "channel": "production" } } }
OTA / CodePush · the real mechanism

How over-the-air bundle updates work

A React Native app is a native shell plus a JavaScript bundle. OTA updates swap the bundle — not the shell. Everything about when it's safe follows from that one fact.

What is “the bundle,” and where is it loaded?

At build time, Metro bundles all your JS/TS into a single file, plus the images Metro packs. That file ships inside the native binary:

PlatformBundle fileLoaded by
iOSmain.jsbundle (in the app bundle)AppDelegate — the sourceURLForBridge / bundleURL method returns the bundle URL (Metro dev server in debug, the embedded file in release).
Androidindex.android.bundle (in assets/)MainApplication — the ReactNativeHost's getJSBundleFile() (defaults to the embedded asset).
The hook that makes OTA possible CodePush/EAS override that bundle location. Instead of always returning the embedded file, sourceURLForBridge (iOS) / getJSBundleFile() (Android) return [CodePush bundleURL] — which points to a newer bundle downloaded to local storage if one exists, and falls back to the embedded bundle otherwise. That's the entire trick: the OS loads whatever file that method returns.

Pointing the app at the OTA bundle

// iOS · AppDelegate.mm
- (NSURL *)sourceURLForBridge:(RCTBridge *)bridge {
#if DEBUG
  return [[RCTBundleURLProvider sharedSettings] jsBundleURLForBundleRoot:@"index"];
#else
  return [CodePush bundleURL]; // downloaded bundle, else embedded main.jsbundle
#endif
}

// Android · MainApplication (ReactNativeHost)
@Override protected String getJSBundleFile() {
  return CodePush.getJSBundleFile();
}

How the app fetches & applies an update

01

Check

codePush.sync() runs (on launch/resume) and asks the update server: “for this app's binary/runtime version and deployment key, is there a newer bundle than the one I'm running?” It sends the current package hash.

02

Download

If yes, the SDK downloads the new JS bundle + assets (often a delta against the current one) into the app's local storage — silently, in the background.

03

Install (timing you choose)

ON_NEXT_RESTART (default) applies on the next cold start; ON_NEXT_RESUME on next foreground; IMMEDIATE restarts now. “Apply” just means the overridden bundle path now resolves to the new file.

04

Confirm or roll back

The new bundle must call codePush.notifyAppReady() (sync does this) to be marked good. If it crashes before that, CodePush automatically reverts to the last working bundle on next launch — your safety net against a bad push.

Integrating CodePush — short pointers

Setup
  1. Create an app + Staging/Production deployments on your CodePush server; grab deployment keys.
  2. npm i react-native-code-push (autolinks native).
  3. iOS: return [CodePush bundleURL] + add key to Info.plist. Android: override getJSBundleFile() + add key to strings.xml.
  4. Wrap the root: export default codePush(App), set checkFrequency / install mode.
Release
  1. Make a JS-only change.
  2. Push to a deployment, targeting the installed binary versions:
    code-push release-react MyApp ios -d Production -t "1.4.x".
  3. Test on Staging, then promote Staging → Production.
  4. Roll out to a % of users; watch crash rate; rollback instantly if needed.
EAS Update alt.
  1. eas update:configure; add expo-updates; set a runtimeVersion policy.
  2. Build with a channel (maps builds → update branch).
  3. Publish: eas update --branch production -m "fix".
  4. App checks on launch, downloads, applies next launch.
The decision · when to reach for OTA

Exactly what you may (and may not) push

The rule is mechanical, not a matter of taste: an OTA bundle is bound to the native binary already installed. Push code that expects native code the binary doesn't have, and it crashes.

At which point do you update the JS bundle?

Only when the change is entirely in the JS layer — JS/TS logic, React components, styling, or Metro-bundled assets (images, JSON). That's when you cut a new bundle and OTA it, skipping store review. If anything native changed, you must ship a new binary through the stores instead — and bump the target/runtime version so old OTA bundles don't land on it.

✓ Safe to OTA

  • Bug fixes in JS/TS, logic, or state.
  • UI tweaks, copy/text, styling.
  • Feature flags & config toggles.
  • New/updated images & assets bundled by Metro.
  • Pure-JS libraries (no native module).

✗ Needs a store binary

  • Any new/changed native module or native dependency.
  • Permissions, entitlements, app icon, splash.
  • React Native version / native SDK upgrades.
  • Anything touching ios/ or android/ native code.
  • Major new features (store-policy territory — see below).

Benefits vs. cons

Benefits

  • ✓ Instant fixes — hours, not a multi-day review cycle.
  • ✓ Phased rollout to a % of users, with metrics.
  • ✓ Instant rollback and auto-revert on crash.
  • ✓ Fast iteration / A-B of JS features.

Cons & limitations

  • ✗ JS + assets only — never native code.
  • ✗ Bundle must match the installed binary/runtime version, or it crashes.
  • ✗ Store policy: Apple 3.3.2 forbids OTA that changes the app's purpose or adds unreviewed features.
  • ✗ Rollback only works if notifyAppReady() is reached.
  • ✗ Extra SDK weight, version sprawl, and a channel you must sign so no one pushes a malicious bundle.
When TO use Emergency JS bug fixes, small UI/copy/config changes, and phased rollout of JS-only features where waiting days for review is unacceptable.
When NOT to use Any native change; large feature launches (ship & get them reviewed); regulated apps that require review of each release; or using OTA to routinely dodge the store — that risks rejection or removal.
Interview Pitfalls

Release & OTA Myths

"CodePush can update the whole app over the air."

False. Only the JS bundle and Metro-bundled assets. Native modules, permissions, and the RN runtime live in the binary and require a store release.

"You can push any JS change to any installed version."

False. A bundle is tied to a target binary/runtime version. If it calls a native module that version doesn't include, it crashes. Always scope releases to compatible binary versions.

"OTA lets you skip App Store review entirely."

Dangerous. Apple guideline 3.3.2 permits OTA of interpreted JS only if it doesn't change the app's purpose or add unreviewed features. Shipping major features OTA to dodge review risks rejection or removal.

"Fastlane is a CI service."

No. Fastlane is automation scripting that still needs a machine to run on. The CI/CD runners are Bitrise, EAS, GitHub Actions, Codemagic — which often execute Fastlane lanes.
