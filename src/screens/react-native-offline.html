Offline-First Architecture

Local first, sync second.

Offline-first flips the usual flow: the UI reads and writes a local database and never blocks on the network. A background sync engine reconciles that local state with the server whenever a connection exists. Four pieces make it work — a local DB, a write outbox, connectivity detection, and a sync engine — and the whole design lives or dies on how you resolve conflicts.

The mental model

The UI never talks to the network

In an offline-first app the network is an implementation detail of syncing, not something screens wait on. Reads and writes hit local storage; the server is reconciled in the background.

Read path

Screens render from local DB queries (ideally reactive, so the UI updates when the DB changes). No spinners waiting on HTTP.

Write path

A user action writes to the local DB immediately (optimistic UI) and appends an intent to the outbox queue. The UI already reflects the change.

Detect

NetInfo reports connectivity changes. On “reachable,” it wakes the sync engine.

Sync engine

Push: flush outbox mutations to the server in order, with retries. Pull: fetch server changes since a cursor and merge into the local DB, resolving conflicts.

Reconcile

Server responses update local rows (confirm, rewrite ids, or override on conflict). The local DB converges toward the server's truth.

The four building blocks

Each piece, in detail

1 · Local database — the source of truth

Everything the user sees comes from here, so it must survive restarts and handle relational data. Key–value stores (MMKV, AsyncStorage) are fine for settings but not for a syncing dataset — you want SQLite or a database built on it. A reactive DB (queries that re-emit when data changes) is what makes optimistic writes feel instant.

2 · Outbox — the write queue

The outbox is an append-only table of intents (“create post”, “like 42”) captured while offline (or always, then flushed). It's the pattern that makes writes durable and ordered. A good outbox row carries:

FieldWhy
id / idempotencyKeyA client-generated UUID so retries don't create duplicates — the server dedupes on it.
type + payloadThe mutation and its arguments, serialized. Replayed against the server on flush.
createdAt / sequencePreserves ordering — “create” must reach the server before its “update.”
status / retryCountpending → in-flight → done/failed, with backoff and a dead-letter after N tries.

3 · Connectivity detection — NetInfo

@react-native-community/netinfo reports connection type and — crucially — isInternetReachable (connected to Wi-Fi ≠ has internet). The sync engine subscribes and flushes on the offline→online transition, rather than polling.

4 · Sync engine — push, pull, reconcile

The engine does two directions. Push drains the outbox sequentially with retry/backoff and marks items done on success. Pull asks the server “what changed since cursor X?”, merges those changes locally, and advances the cursor. The hard part is what happens when both sides changed the same record — conflict resolution.

Conflict strategyHowTrade-off
Last-Write-Wins (LWW)Compare timestamps/version; newest wins.Simplest; silently drops the losing edit. Fine for single-user data.
Server-authoritativeServer rejects stale writes (409); client refetches and reapplies.Predictable and safe; needs conflict UX and a version column.
CRDT / mergeableData types that merge automatically (used by ElectricSQL, Yjs).No lost edits, true multi-writer — but heavier model and library lock-in.

Which is best?

There's no single winner — it's a fit to your backend and scale:

Default choice

WatermelonDB

For most custom-backend RN apps with lots of relational data. Mature, reactive, scales, and its sync protocol handles the push/pull plumbing while leaving you in control of the server.

Least infra

PowerSync / ElectricSQL

If you're on Postgres and don't want to hand-write a sync engine, a managed Postgres⇄SQLite service gets you there fastest, with conflict handling built in.

Small / simple

SQLite + outbox

For a handful of screens and simple mutations, raw SQLite (op-sqlite/expo-sqlite) with a hand-rolled outbox and LWW is lighter than adopting a whole framework.

Roll your own (SQLite + outbox)

  • ✓ Full control over schema, ordering, conflict rules.
  • ✓ No framework lock-in or extra service.
  • ✗ You own all the hard parts: ordering, retries, dedupe, conflicts, cursors.
  • ✗ Easy to get subtly wrong (duplicate writes, lost updates).

Turnkey sync engine

  • ✓ Conflict handling, retries, and reactivity solved for you.
  • ✓ Much faster to a correct offline experience.
  • ✗ Adopt their data model & server contract; possible vendor/deprecation risk.
  • ✗ Less control when your case doesn't fit the framework's assumptions.
Integration · the outbox path end to end

Wiring it up

Steps for the build-your-own approach (the concepts are identical if a framework does the plumbing).

01

Install the pieces

A local DB (@op-engineering/op-sqlite, expo-sqlite, or WatermelonDB), @react-native-community/netinfo, and a UUID lib for idempotency keys.

02

Model tables: domain + outbox

Your domain tables (posts, todos…) plus an outbox table with id/idempotencyKey, type, payload, createdAt, status, retryCount, and a sync_cursor for pulls.

03

Render from local, reactively

Screens subscribe to local queries. No component awaits fetch. Loading states become “is the initial sync done,” not “is this request pending.”

04

Write locally + enqueue

On a mutation: update the domain row optimistically and insert an outbox row in the same transaction, so the intent can never be lost if the app dies mid-write.

05

Flush on reconnect

A NetInfo listener (and app-foreground) triggers the push loop: send outbox items in order with the idempotency key, retry with backoff, mark done, dead-letter permanent failures.

06

Pull & reconcile

Ask the server for changes since the cursor, merge into local tables with your conflict rule, advance the cursor. Reconcile temporary client ids with server ids.

Optimistic write + durable outbox (one transaction)

import NetInfo from '@react-native-community/netinfo';
import { randomUUID } from 'expo-crypto';

async function createTodo(text) {
  const id = randomUUID();
  await db.transaction(async (tx) => {
    // 1. optimistic local write — UI updates instantly
    await tx.execute('INSERT INTO todos (id, text, synced) VALUES (?, ?, 0)', [id, text]);
    // 2. durable intent in the SAME transaction
    await tx.execute(
      'INSERT INTO outbox (id, type, payload, created_at, status) VALUES (?, ?, ?, ?, ?)',
      [randomUUID(), 'todo.create', JSON.stringify({ id, text }), Date.now(), 'pending']
    );
  });
  const net = await NetInfo.fetch();
  if (net.isConnected && net.isInternetReachable) flushOutbox(); // else: on reconnect
}

Push loop — ordered, idempotent, with retry

async function flushOutbox() {
  const items = await db.getAll(
    "SELECT * FROM outbox WHERE status = 'pending' ORDER BY created_at ASC"
  );
  for (const item of items) {
    try {
      await api.post('/mutations', JSON.parse(item.payload), {
        headers: { 'Idempotency-Key': item.id }, // server dedupes retries
      });
      await db.execute("UPDATE outbox SET status = 'done' WHERE id = ?", [item.id]);
    } catch (e) {
      if (item.retry_count >= 5) await deadLetter(item);   // give up, surface to user
      else await bumpRetry(item);                            // backoff, try later
      break; // preserve ordering — stop on first failure
    }
  }
}
Interview Pitfalls

Offline-First Myths

"Offline support just means caching API responses."

Incomplete. A read cache handles reads, not writes. Offline-first means the local DB is the source of truth and mutations are queued durably (outbox) and synced — otherwise offline edits are lost.

"NetInfo says connected, so I can sync."

Not necessarily. A device on captive-portal Wi-Fi is “connected” but has no internet. Check isInternetReachable, not just isConnected, before flushing.

"Retrying failed mutations is safe."

Only with idempotency keys. Without a client-generated key the server dedupes on, a retry after a dropped response creates duplicate records. Every outbox item needs a stable idempotency key.

"Last-Write-Wins is a fine default for everything."

Risky. LWW silently discards the losing edit — dangerous for shared/multi-user data. Use server-authoritative versioning or CRDTs when concurrent edits matter.
