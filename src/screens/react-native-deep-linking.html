Deep Linking Architecture. Schemes, Universal & App Links.

A deep link routes a URL to a specific screen inside your app. The hard parts aren't the routing — they're proving to the OS that you own the domain, putting the verification files in exactly the right place, handling links that arrive before the app is installed, and not trusting a single byte of what the link contains.

myapp:// Universal Links (iOS) App Links (Android) /.well-known/ AASA + assetlinks.json Deferred · Branch.io
Three Types of Deep Links

Deep Link Architecture Comparison

Three mechanisms, escalating in reliability and trust. Interviewers want you to know not just what they are, but why each one exists.

Legacy / Basic

Custom URL Schemes

URLs like myapp://profile/123. Trivial to register in the native manifest. But any app can claim the same scheme, browsers show a warning prompt, and if the app isn't installed the link just fails — no web fallback.

Modern Standard

Universal & App Links

Ordinary HTTPS URLs (https://myapp.com/profile/123), verified by the OS against a file you host on the domain. Opens the app if installed, otherwise the website — and can't be hijacked, because ownership is proven server-side.

Deferred Attribution

Deferred Deep Links

Preserves the destination when the user taps a link before the app exists on their device. After they install from the store and open, the app recovers the original target and navigates there. Requires a third-party SDK — the OS can't do it alone.

The mechanism

What actually happens on a tap

The difference between a scheme and a universal link is entirely about who decides the app is allowed to handle the URL.

Custom scheme

The OS sees myapp://, looks for any installed app that registered that scheme, and opens it. No verification — an ambiguous match can go to the wrong app, which is the hijacking hole.

Universal link (iOS)

On app install, iOS fetches https://myapp.com/.well-known/apple-app-site-association and checks that your app's appID is listed. Only then will tapping an https://myapp.com/... link open your app instead of Safari.

App link (Android)

With android:autoVerify="true", Android fetches https://myapp.com/.well-known/assetlinks.json and matches your package name + signing-cert fingerprint. Verified links skip the “open with” chooser entirely.

Why HTTPS links are the answer to hijacking A custom scheme is a claim; a universal/app link is a proof. Because the OS won't associate the domain with your app unless it can fetch a file that only the domain owner could have placed there, no rogue app can intercept your https:// links. This is the single most common deep-linking interview point.
React Navigation Setup

Routing links into screens

Once the OS hands your app a URL, React Navigation's linking config maps it to a screen. You must handle both cold start and warm (already-running) cases.

import { NavigationContainer, LinkingOptions } from '@react-navigation/native';
import { Linking } from 'react-native';

const linking: LinkingOptions<RootStackParamList> = {
  prefixes: ['myapp://', 'https://myapp.com', 'https://www.myapp.com'],
  config: {
    screens: {
      Home: '',
      Profile: 'user/:userId',
      PostDetails: {
        path: 'posts/:postId',
        parse: { postId: (id) => Number(id) },
      },
    },
  },
  // Cold start: app was launched *by* the link
  async getInitialURL() {
    return await Linking.getInitialURL();
  },
  // Warm start: link arrives while app is already open
  subscribe(listener) {
    const sub = Linking.addEventListener('url', ({ url }) => listener(url));
    return () => sub.remove();
  },
};

export default function App() {
  return <NavigationContainer linking={linking}>{/* screens */}</NavigationContainer>;
}
The bug everyone ships once Handling only getInitialURL() works when the app is closed, but does nothing when it's already running in the background — the link silently no-ops. You need both getInitialURL (cold start) and the url event subscription (warm start). React Navigation's linking prop wires up both for you; if you roll your own with the raw Linking API, you must do both by hand.
Server verification · where the files live

The /.well-known/ folder

This is the part people get wrong. The OS looks for your verification files at one exact, standardized location. Miss any detail and links silently fall back to the browser with no error.

/.well-known/ is a standardized directory (RFC 8615) at the root of your domain reserved for machine-readable metadata — the same place SSL/ACME challenges, security.txt, and passkey configs live. Apple and Google both look here for the app-association files. It is served by your web server / host, not bundled inside the app.

https://myapp.com/ └── .well-known/ ├── apple-app-site-association # iOS — NO .json extension └── assetlinks.json # Android

The rules that make or break it

RequirementWhy
Exact path /.well-known/…Both OSes fetch this specific location. It must be on the apex/exact domain the link uses (myapp.com vs www.myapp.com are different — register both if you link both).
HTTPS with a valid certFetched over TLS only. Self-signed or expired certs fail verification.
Content-Type application/jsonRequired for the AASA even though it has no .json extension. A wrong MIME type is the most common iOS failure.
No redirectsApple's CDN and Android's verifier fetch the file directly. A 301/302 (e.g. http→https or apex→www) breaks it. Serve 200 OK at the real path.
Publicly reachable, no authNo login walls, no geo-blocking, no robots/WAF blocking the store's fetchers.
iOS · apple-app-site-association

Modern format uses components (path, query, fragment matching). appID is <TeamID>.<BundleID>. Also add the Associated Domains entitlement applinks:myapp.com in Xcode.

{
  "applinks": {
    "details": [{
      "appID": "TEAMID.com.myapp",
      "components": [
        { "/": "/user/*" },
        { "/": "/posts/*" }
      ]
    }]
  }
}
Android · assetlinks.json

Needs the SHA-256 fingerprint of the signing cert. With Play App Signing, use the fingerprint from the Play Console (not your local upload key). Add an intent-filter with android:autoVerify="true".

[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "com.myapp",
    "sha256_cert_fingerprints": ["AB:CD:EF:..."]
  }
}]

Heads up: caching & timing iOS fetches the AASA at install time through Apple's CDN, which caches aggressively — changes can take a while to propagate, and you often need to reinstall the app to re-trigger the fetch. Android verifies on install too; use adb shell pm verify-app-links --re-verify com.myapp to force re-verification while debugging.
The one nobody can define

Deferred deep linking, explained

Plainly: a deferred deep link is a deep link whose destination is remembered across an app install. The navigation is “deferred” until after the app exists.

A normal deep link assumes the app is already installed. But the most valuable moment is a user who taps myapp.com/posts/42, doesn't have the app, gets sent to the App Store, installs, and opens it — landing on the generic home screen, the shared post lost. Deferred deep linking closes that gap: it carries the original destination (and marketing attribution) through the install so the first launch opens post 42.

Why you need a third party for it

Neither iOS nor Android natively passes link data through a store install — for privacy, there's no durable identifier connecting “the browser that clicked” to “the app that just launched.” So an attribution SDK bridges the two.

1 · Click

User taps a Branch link (myapp.app.link/xyz). Branch records the click plus the intended deep-link data and any campaign params, then redirects to the correct store.

2 · Install

User installs and opens the app. The Branch SDK initializes on first launch and asks Branch's server: “does this new open match a recent click?”

3 · Match

Branch matches click → open — deterministically on Android (Play Install Referrer) and via other signals on iOS — and returns the stored deep-link data.

4 · Route

Your app reads the returned params in the SDK callback and navigates to the real destination. First launch lands on post 42, not Home.

Branch.io — and where you configure it

Branch is the most common choice (alternatives: AppsFlyer OneLink, Adjust; Firebase Dynamic Links is being shut down, so don't pick it for new work). Configuration lives in two places: the Branch dashboard and your app.

WhereWhat you set up
Branch dashboardYour link domain (myapp.app.link or a custom subdomain), the iOS Bundle ID + App Store ID, Android package + SHA-256, default deep-link data, and redirect/fallback rules.
iOS projectAdd the Branch key to Info.plist, add the Branch link domain to your Associated Domains entitlement (Branch hosts the AASA for its domain), and init the SDK in AppDelegate.
Android projectAdd the Branch key to the manifest, register an intent-filter for the Branch link domain, and initialize in your Application class.
JS / React NativeSubscribe to the SDK's session callback; it fires on every launch with +clicked_branch_link and your custom params.

Reading the deferred link in React Native

import branch from 'react-native-branch';

// Fires on cold start AND when a Branch link opens the app.
const unsubscribe = branch.subscribe(({ error, params }) => {
  if (error) return;
  // True only when the app was opened via a Branch link
  if (params['+clicked_branch_link']) {
    const target = params.$deeplink_path;   // e.g. "posts/42"
    navigateFromUrl(target);                       // works even on first-ever launch
  }
});
One-line interview answer “A deferred deep link remembers where the user was headed across the install — they tap a link without the app, install from the store, and the first launch still opens the right screen. The OS can't carry that context through an install, so you use an attribution SDK like Branch.io to match the pre-install click to the post-install open and hand your app the original deep-link data.”
Security · treat every link as hostile

Deep links are untrusted input

A deep link is an entry point into your app that anyone can craft and send by SMS, email, or a web page. Handle its contents with the same suspicion as a query string on a public API.

Scheme hijacking

Prefer verified links

Any app can register myapp:// and intercept it. Use Universal / App Links (OS-verified domain ownership) for anything sensitive. Keep the custom scheme only as a convenience/fallback, never as your trust boundary.

Blind trust in params

Validate & authorize

Never perform a privileged action straight from a link. myapp://delete-account or ?userId=999 must still pass authentication and server-side authorization. The link chooses a screen; it does not grant permission.

Open redirect

Allowlist redirects

If a link carries a redirect or next URL, validate it against an allowlist of your own hosts. An unchecked redirect turns your app into a phishing launchpad.

Injection & traversal

Sanitize before use

Coerce and bound types (Number(postId)), reject unexpected shapes, and never feed raw link params into file paths, DB queries, or WebView URLs. Escape/validate at the boundary.

Secrets in the URL

Don't ship tokens in links

Links land in logs, analytics, clipboards, and referrers. Magic-link / auth tokens must be single-use, short-lived, and server-validated — treat the link as a hint to start a flow, not proof of identity.

Defense in depth

Re-check on the server

The client can be bypassed entirely (attackers call your API directly). Every action a deep link can trigger must be independently authorized on the backend. The link is UX; the server is the gate.

Validate at the boundary before you navigate

function handleDeepLink(url) {
  const { pathname, searchParams } = new URL(url);

  // 1. Only accept paths you actually own
  if (!ALLOWED_PATHS.test(pathname)) return goHome();

  // 2. Coerce & bound every param — never trust the raw string
  const postId = Number(searchParams.get('postId'));
  if (!Number.isInteger(postId) || postId <= 0) return goHome();

  // 3. Gate protected destinations behind auth + server authz
  if (isProtected(pathname) && !isAuthenticated()) {
    return goToLogin({ returnTo: pathname });
  }

  navigate(pathname, { postId });
}
Interview Pitfalls

Deep Linking Myths

"Custom URL schemes can't be hijacked by other apps."

False. Multiple apps can register the same custom scheme (myapp://). Universal / App Links solve this because the OS verifies domain ownership via a file only you can host.

"The AASA file is named apple-app-site-association.json."

False. It has no extension — just apple-app-site-association — served with a Content-Type: application/json header from /.well-known/ over HTTPS with no redirects.

"Deferred deep linking is a built-in feature of iOS/Android."

False. The OS does not carry link data through a store install. Deferred deep linking is provided by attribution SDKs (Branch, AppsFlyer, Adjust) that match a pre-install click to the post-install first open.

"If the link opened my screen, the user is authorized to be there."

False. A link is attacker-controllable input. Authentication and authorization must be enforced independently, on the server — the deep link only selects a destination.

Senior Technical Scenario

End-to-end walkthrough

💬 Question: "Marketing sends a campaign link to a shared post. It must open the exact post if the app is installed, open the website on desktop, and — if a mobile user doesn't have the app — install it and still land on that post. Walk me through it."
Plan:
  1. Use HTTPS Universal/App Links, not a custom scheme, so the OS opens the app directly and the same URL works as a website fallback on desktop.
  2. Host the verification files at https://myapp.com/.well-known/apple-app-site-association (Content-Type application/json, no extension, no redirects) and /.well-known/assetlinks.json (with the Play signing SHA-256). Add Associated Domains on iOS and autoVerify on Android.
  3. Map the path in React Navigation (posts/:postId) and handle both cold start (getInitialURL) and warm start (url event).
  4. For the not-installed case, wrap it as a Branch link so the destination is deferred through the store install; read $deeplink_path in branch.subscribe on first launch and route to the post.
  5. Validate before navigating: confirm the path is one we own, coerce postId to a positive integer, and gate any private post behind auth with a returnTo back to the link.
  6. Verify with Apple's AASA validator and Google's Digital Asset Links API, and test a real install-from-store flow — not just an already-installed device.
