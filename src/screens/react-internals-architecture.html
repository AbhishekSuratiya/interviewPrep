End-to-End Pipeline

From JSX to Browser Pixels, Step by Step

The complete multi-phase journey of every component render and state update in modern React.

01

JSX Compilation & Runtime Element CreationBuild Time & Render Time

Babel/SWC transpiles JSX into runtime function calls (_jsx or React.createElement). Executing these returns a plain, immutable JS object: { $$typeof: Symbol(react.element), type, props, key, ref }. It is a lightweight description of UI, NOT a DOM node.

02

State Update Scheduling & Priority Lane AllocationJS Thread

Calling setState schedules a re-render. React assigns a bitmask priority lane (e.g. SyncLane for click/typing, TransitionLane for startTransition). Work is queued on the target Fiber node.

03

Render Phase: Fiber WorkLoop ExecutionInterruptible

React runs workLoopConcurrent, walking Fiber nodes via child, sibling, and return pointers. beginWork runs component functions and diffs elements; completeWork creates in-memory DOM nodes and bubbles effect flags. Crucially, after processing each Fiber, React calls shouldYield() (~5ms budget). If true, it yields back to the browser!

04

Double Buffering & Tree SwapHeap Memory

React maintains two trees: current (on screen) and workInProgress (building). Each Fiber has an .alternate pointer to its counterpart. If an urgent update interrupts render, React simply discards the WIP tree with zero DOM cleanup side-effects because the DOM was never touched!

05

Commit Phase: Synchronous DOM MutationsSynchronous / Atomic

Once render completes cleanly, React enters the Commit Phase (uninterruptible):
• BeforeMutation: Reads DOM snapshots (getSnapshotBeforeUpdate).
• Mutation: Applies DOM insertions, updates, and deletions. Swaps current = workInProgress.
• Layout: Fires useLayoutEffect synchronously before browser paint.

06

Browser Paint & Passive EffectsMain Thread

The browser repaints pixels to the display screen. Immediately post-paint, React schedules and fires useEffect passive cleanup and setup callbacks asynchronously so user interaction is never blocked.

Myth Busting

7 Common React Misconceptions Busted

Clarifying deep architectural nuances commonly tested in senior frontend interviews.

Myth 1: "Props changing is what triggers a component re-render."
Reality: Re-renders are triggered by state updates, context changes, or parent re-renders. When a parent re-renders, ALL children re-render by default regardless of whether props changed. React.memo is an opt-in check to prevent this.
Myth 2: "Fiber changed React's diffing algorithm."
Reality: The diffing heuristics (type identity check, keys for lists, unmount on type mismatch) are IDENTICAL before and after Fiber. Fiber changed the reconciler architecture (how work is scheduled & traversed), not the diff rules.
Myth 3: "Concurrent React means multi-threaded parallel execution."
Reality: JavaScript remains strictly single-threaded. Concurrency in React means interleaved execution — React works in short ~5ms time slices, yields control via MessageChannel macrotasks, and resumes.
Myth 4: "MessageChannel yields work using Microtasks (Promise.then)."
Reality: Microtasks drain completely before browser paint, which would lock the UI thread. React uses MessageChannel (or scheduler.postTask) to schedule Macrotasks, letting the browser paint and handle inputs between 5ms slices.
Myth 5: "The old Virtual DOM tree is the real HTML DOM."
Reality: The old virtual tree is React's in-memory heap representation of what was last committed. The real DOM lives inside the browser C++ engine.
Myth 6: "Keys are global unique identifiers that re-render components."
Reality: Keys are scoped strictly to sibling array elements. Changing a key forces React to unmount and remount a fresh instance (destroying state), not re-render.
Myth 7: "Concurrent rendering makes total CPU work faster."
Reality: Concurrent rendering increases or keeps total CPU work equal due to potential restarts. What it improves is input latency and responsiveness by prioritizing urgent work.

Stack Reconciler vs Fiber Reconciler

Side-by-side technical breakdown of React's reconciler architectures.

Architectural Axis Pre-React 16 (Stack Reconciler) React 16+ (Fiber Reconciler)
Traversal Mechanism JS Call Stack (Recursive function calls) Heap Linked List (child, sibling, return pointers)
Interruptibility Uninterruptible (Sync to completion) Interruptible Render Phase (yields via workLoop)
Yield Mechanism None (Locks main thread during long renders) MessageChannel macrotasks (~5ms time slice budget)
Tree Architecture Single Tree (Mutates native DOM imperatively) Double-buffered (current & workInProgress alternate trees)
Priority Support FIFO (All state updates execute sequentially) Bitmask Priority Lanes (Sync, Input, Transition, Idle)
Diffing Heuristics O(n) Heuristic (Type identity & Keys) O(n) Heuristic (Identical rules preserved)
